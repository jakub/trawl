# A query's regex work is bounded before it runs

status: accepted (2026-11-02), prep record for the regex cost fix; human rulings of 2026-11-02 recorded below; amended 2026-11-03 (human ruling): the repeat budget is 64 positions and the per-call ceiling about 0.4 s; amended 2026-11-03 under that ruling: every node that compiles to an instruction counts toward the budget, an alternation's splits included, and the batch `extract` reads named groups among themselves; amended 2026-11-04 (human rulings of 2026-11-03 and 2026-11-04): nested classes and class set operators are refused, the batch engine's view of a body is capped at 512 KiB, the per-call ceiling is 0.5 s for the Rust engine only with RE2 a measured envelope, and a timed-out batch regex can keep its slot past its deadline until 1.1; amended 2026-11-04, later (human rulings of 2026-11-04): the regex memory bounds are calibrated, DuckDB's RE2 counts in the server-wide reservation by kind of site, and an `extract` binds one RE2; amended 2026-11-04, after the final security review (human ruling): the regexes the emitter writes itself count too, at a measured 9 KiB a call

The ADR-0060 amendment bounds how many patterns a query holds (256) and how large one regex compiles (1 MiB). It left four items open for a separate 1.0 issue: `matches` recompiles its regex for each event, a computed `matches` operand is not counted, `extract` regexes skip the 1 MiB constructor, and translating a `(?i)` regex over a large Unicode class costs time that no size limit bounds. The human ruled this a 1.0 blocker with one subject: a query cannot spend unbounded CPU or memory through regexes.

Scouts and both design legs measured these on main (`06d672f2`, regex 1.13.1, regex-automata 0.4.16, DuckDB 1.5.6):

- **Event-time builds.** `eval_matches` (`eval.rs:850`) and `eval_like` (`eval.rs:882`) call `Regex::new` on every event. `\w+@\w+\.\w{2,10}` costs 1.94 ms per event to build and 11 ns to match once built. A pattern that does not compile matches nothing and raises no error. The batch Rust tail behind `extract kv` runs the same evaluator.
- **Bodies that skip validation.** A quoted `matches "re"` body and every `extract` body bypass the 1024-byte body limit and the 1 MiB constructor. `extract` builds with plain `Regex::new`, whose default program limit is 10 MiB, at five sites (`emitter/validate.rs:96`, `emitter/pipeline.rs:302`, `pin_scope.rs:263`, `stream.rs:956`, and the glob adapter at `filter.rs:348`). A 64 KiB `extract` body costs about 30 s to build, and one `/query` builds it about five times.
- **Translation cost.** `(?i)` with `\p{Any}` repeated to a 1019-byte body takes 440 ms to translate and then compiles under 1 MiB. 63 such bodies fit in the 64 KiB query cap and cost about 27 s per parse. One `/query` parses two times on the async reactor and three or four times on the blocking pool. A sixth parse happens for saved sources. The cost comes from case-folding full-range classes before the 1 MiB check runs, so body length is the wrong measure: `\p{Any}` costs 0.43 ms per byte and an ASCII class costs almost nothing.
- **Matching cost.** Matching time is linear in the subject, but the constant grows with counted repeats. `(?:a|b)[abc]{1000}(?:a|d)d` is 27 bytes, passes every current limit, and costs 4.2 s per MiB of subject in Rust. The `{30}` form costs about 200 ms per MiB in Rust and in DuckDB RE2. Ingest accepts bodies up to 16 MiB, and only `_raw` has a length cap (`MAX_RAW_CHARS`, 65 536 characters). So one admitted pattern can spend tens of seconds on one field of one event.
- **The reactor.** `check_dsl`, `/validate` and SSE setup parse on tokio reactor threads with no permit. SSE setup parses twice. Live evaluation, including every per-event build, runs inside the SSE stream's poll. One slow call parks a reactor thread, and a few concurrent requests can park all of them, which stalls health and metrics too.
- **Memory.** No regex sets a lazy-DFA capacity, so each cache can grow to 2 MiB forward and 2 MiB reverse. A regex pools up to nine caches across threads. 256 distinct `\w{20}…` regexes used about 458 MiB on one thread. Every SSE stream compiles its own copies, and `max_sse_connections` defaults to 32. ADR-0056's memory ledger has no row for regex state.
- **Extract group indices.** For `extract "(a|b)(?P<x>b)-(?P<y>c)"` on `ab-c`, the batch emitter binds `x` to group 1, which is the unnamed group, while the live lane reads `x` by name and gets `b`. The two lanes disagree.

## Decision

**One owner builds every regex, and nothing else may.** A `Pattern` type in `trawl-core` owns construction for search-stage regexes, `matches` operands, `like` and `ilike` patterns, `extract` bodies and the glob adapter. A clippy `disallowed-methods` rule bans `regex::Regex::new`, `regex::RegexBuilder::new` and the `regex-automata` builders outside the owner module. An inventory test lists every construction site, so a new one fails CI until someone adds it on purpose.

**A pattern is always literal text in the query (human ruling, 2026-11-02).** The right side of `matches`, `like` and `ilike` must be a literal in every lane. `matches lower("a")` and `matches field` are parse errors with a hint. The emitter refuses a hand-built AST with a computed pattern with a typed error, so the rule does not depend on `parse` having run. The literal `regexp_matches` emission path stays; only computed operands lose it.

**Every regex body gets the same validation.** A quoted `matches "re"` body and an `extract` body pass the same checks as a `/body/` regex, in the same order: syntax, the 1024-byte body limit, the budgets below, then the 1 MiB compile. A raw glob, `like` or `ilike` operand may be 1024 bytes long. Each check is a parse error with a span and a message of its own.

**Admission prices a query's regex work before any translation.** After the syntax pass, which is linear and compiles nothing, one walk over the regex ASTs with an explicit stack computes three numbers. Calibration sets the limits, and the evidence states each one.

- **A translation budget per query.** It is a weighted sum of range materialisation, case-fold work under `(?i)`, case-insensitive literals and class set operations. It follows the pinned `regex-syntax` translator: Perl classes (`\w`, `\d`, `\s`) are already closed under case folding, and the translator never folds them, so they pay range cost and no fold cost. Where the walk cannot know the translated shape, it charges the maximum. A negated class whose complement is one character, as in `(?i)[^\x00-\x{10FFFE}]`, still pays the full fold of its positive side. The candidate limit is 2^24 units, about 50 ms of translation on the reference host. The limit admits ordinary `(?i)` syslog and email regexes, 256 of them included, and refuses the measured attacks: 63 `\p{Any}` bodies, 64 KiB of `(?i)\p{Ll}`, 64 KiB of `\w`, and full-range brackets. (Amended 2026-11-03: under the 64-position repeat budget, 64 KiB of `\w` no longer reaches this budget. A body of more than 64 `\w` is refused for its repeats, and 256 bodies of 64 pass both budgets, then fail the compiled-size limit at the first build.) An inventory test maps every case-fold call site in the pinned `translate.rs` to a charge, so a dependency bump that adds one fails the test.
- **A repeat budget per pattern (human ruling, 2026-11-02).** It caps the repetition-expanded position count: each atom counts once, multiplied by its counted repeat's upper bound. An unbounded repeat counts its lower bound plus one. The limit is 64 positions (amended 2026-11-03; the candidate was 256, which the measured cost refused). `(?:a|b)[abc]{1000}(?:a|d)d` and `[A-Za-z]{1000}` are refused with a hint to write `+` or a shorter count. `\d{1,3}(\.\d{1,3}){3}`, a UUID and `[0-9a-f]{64}` are admitted.
- **Fan-out against the existing 256 cap.** An `extract` counts `max(1, named groups)` toward `MAX_QUERY_PATTERNS`, because the batch lane emits one `regexp_extract` per named group. (Amended 2026-11-04, later: the batch lane now binds an `extract` once, whatever its group count, and the charge per named group stays. See that amendment.) The other operators keep their current charges. An emit-time counter refuses the 257th regex-bearing parameter, or a regex parameter total over 256 KiB, before it allocates, because lateral expansion (ADR-0024) can copy one written pattern into several SQL expressions.

Construction stops after the first build that fails for size, and the translation work it spent counts against the budget. A query of 256 sites that each fail the 1 MiB check therefore costs one failed build, not 256.

**Capture names and indices come from the AST.** Validation, emission and pin-scope advancement read `extract` capture names and absolute group indices from the regex syntax tree and compile nothing. The batch emitter uses absolute indices, which fixes the mixed named and unnamed group divergence.

**Live evaluation never builds a regex.** Each compiled stage owns a table of prepared patterns, built once when the plan compiles. `where`, `let`, `like`, `ilike`, regex `extract` and the `extract kv` tail look patterns up in that table. A missing entry is a typed error, never a non-match and never a lazy build.

**Ingest caps every stored string value (human ruling, 2026-11-02).** The canonicalizer applies the `_raw` cap, `MAX_RAW_CHARS` (65 536 characters, so at most 256 KiB), to every string value it stores. It cuts at a character boundary and records the existing actionable repair `field.truncated` (ADR-0055), which until now applied to `_raw` only. Together with the repeat budget, one regex call over one stored value costs at most about 0.4 s (amended 2026-11-03; the prep claimed 0.25 s at 256 positions; amended 2026-11-04: at most 0.5 s in the Rust engine, and a measured envelope of about 1.8 s with no ceiling in DuckDB's RE2). Data stored before the upgrade keeps its long values. A query over them stays correct and pays the higher cost, which the cancellation points below still bound per call (amended 2026-11-04: in DuckDB, per 2048-row vector).

**Regex memory has a per-query budget and a server-wide reservation.** `Pattern` is backed by `regex-automata`'s meta engine with caches that each prepared query owns explicitly, not the implicit per-thread pool. A per-query budget covers compiled programs, both lazy-DFA directions, fallback scratch, compiler transients and duplicate copies. The candidate is 16 MiB. Cache capacity derives from that budget and stays above `regex-automata`'s minimum for each pattern, so the lazy DFA stays on for ordinary patterns, and the evidence records the measured tail throughput at the chosen value. A server-wide reservation, candidate 256 MiB, is charged before matching starts and released when the physical work ends. It becomes a fixed row in ADR-0056's memory ledger. A query that cannot reserve its budget is refused with 503 `query_resource_exhausted` and a regex cause, distinct from a DuckDB memory refusal. (Amended 2026-11-04, later: the budget is 32 MiB and the reservation 1.25 GiB, with at most 512 MiB for one query, and capacity follows each pattern's own minimum. See that amendment.)

**DuckDB RE2 memory ships as a measured envelope (human ruling, 2026-11-02).** The batch lane's `regexp_matches` and `regexp_extract` run in DuckDB's RE2, which may allocate outside `query_memory_limit`. The implementation measures what RE2 retains per expression and per thread under the admitted worst case and records it. If DuckDB exposes no hard limit, the ADR-0056 ledger states the measured envelope as a residual risk. 1.0 ships with it. (Amended 2026-11-04, later, by human ruling: the measured worst case did not fit the ledger, so a batch query now holds an RE2 allowance from the server-wide reservation. See that amendment.)

**Preparation never runs on the reactor.** Every server door that parses query text runs parse, validation and pattern preparation on the blocking pool behind a preparation allowance. That covers `/query`, `/validate`, SSE setup, export, saved-query create and update, capture planning, the scheduler and the MCP tools. The allowance is sized from available parallelism: half the cores, at least 2, at most the executor permits. A job waits for a slot within its request's deadline, then gets 503. A job that times out keeps its slot and its memory reservation until its closure exits. This amends ADR-0054.

**Live matching runs in bounded jobs off the reactor.** The SSE stream hands events to the blocking pool in bounded chunks. Each stream has at most one outstanding job and a bounded handoff queue. Calibration over long subjects and rejected events sets the chunk size. Order and aggregation state survive chunk boundaries.

**Cancellation is cooperative, and one call is the unit that cannot be stopped (human ruling, 2026-11-02).** Neither Rust regex nor RE2 can be interrupted inside one call. Preparation checks for cancellation between translations, builds and planning phases. Live jobs check between regex calls. The batch Rust tail checks between events and between stages. The leftover is one regex call over one stored value, bounded by the repeat budget and the field cap. (Amended 2026-11-04: DuckDB checks for an interrupt only between 2048-row vectors, so in the batch lane the leftover is the rest of one vector on each query thread until 1.1; see the 2026-11-04 amendment.) A hard physical stop would need a separate process that can be killed, and 1.0 does not promise one.

**Refusals keep their envelopes.** `/validate` answers 200 with `valid: false` and the parse error for every new admission refusal, as it does for other parse errors. Only capacity refusals are 503.

**MCP hints compile nothing from stored text.** Reading a capture or saved query for optional hints (`hints.rs`) does not build the historical query's regexes.

**`check_dsl` returns the parsed query.** Saved-source detection and SSE setup reuse it instead of parsing again. Carrying one prepared query through source selection, the executor, severity metadata and MCP, so that a request parses once, is later work. It cuts latency and does not change the bound, because every remaining parse is priced and runs off the reactor.

**Stored data and stored query text change on upgrade.** After the upgrade, ingest cuts string values over the cap. A rollback cannot recover the cut bytes, because they were never stored. Saved queries, schedules, investigation steps and captured results may hold a computed pattern, a long counted repeat, a long glob or an `extract` body over 1024 bytes. Each one fails its next validation or run with its diagnostic. Restoring the old behaviour for stored queries means restoring the Postgres database and `[server] results_dir` together, taken with trawld stopped. The pull request that makes each change names that pair in its Revert section.

**The work ships as three pull requests, in order (human ruling, 2026-11-02).**

1. Admission: the `Pattern` owner and its lint, literal-only operands, uniform body validation, the three budgets, AST capture metadata and the index fix, compile-once live tables, the ingest field cap, the `/validate` envelope, MCP hints, and `check_dsl` reuse.
2. Memory: the meta-engine backing, the per-query budget, the server-wide reservation, cache sizing, and the RE2 measurement.
3. Scheduling: preparation off the reactor, live jobs off the reactor, cancellation points, and slot and reservation ownership. It completes this decision and discharges the ADR-0060 amendment's open paragraph.

**The evidence counts work, not wall time.** A query-scoped build counter, not a thread-local one, proves one build per unique pattern across preparation and live jobs. Barrier tests prove slot and reservation ownership. A current-thread runtime test proves unrelated async work runs while a preparation job is parked. Wall-clock and RSS measurements are committed transcripts on a named host, kept out of the shared CI gate.

Considered and rejected:

- **Keep computed operands with a per-event compile budget.** It needs a budget in Rust and in RE2 for patterns that do not exist until data arrives. The human chose literal-only.
- **A fold-only unit with 8 units per body and 32 per query.** It charges Perl classes for folding the translator never does, so it refuses an ordinary `(?i)` syslog regex, and it leaves range materialisation without `(?i)` uncharged.
- **Separate capture limits of 32 per pattern and 128 per query.** Charging named groups to the existing 256 cap gives the same fan-out bound without refusing a 40-field access-log parser.
- **A per-subject cap at query time.** One oversized event would then fail every regex query over its time range. The bound belongs where the data enters.
- **No subject bound.** One call over a 16 MiB field at the admitted worst case costs tens of seconds.
- **A two-slot preparation allowance that refuses at once.** Two heavy requests would get every other request refused.
- **A fixed 16 KiB lazy-DFA cache.** Below `regex-automata`'s minimum capacity the lazy DFA turns off, and ordinary live patterns fall back to the much slower PikeVM.
- **Leave preparation on the reactor because repeated parses are a constant factor.** With admission alone, one parse can still spend about 0.85 s compiling near-limit patterns on a reactor thread, and SSE setup does it twice.
- **A hard deadline through a killable worker process.** It changes the architecture. The human chose cooperative cancellation with a bounded unit.

ADR-0060's amendment is discharged when the third pull request lands. ADR-0055's `field.truncated` now covers every string value. ADR-0054 gains the preparation allowance. ADR-0056's memory ledger gains the regex reservation row. ADR-0001 still holds: the regex dialect difference between lanes (Rust Unicode classes, RE2 ASCII) is unchanged and out of scope.

## Amendment (2026-11-03): the repeat budget is 64 positions

Human ruling, 2026-11-03. The repeat budget is 64 positions per pattern, and the ceiling on one regex call over one capped value is about 0.4 s. (The 2026-11-04 amendment sets that ceiling at 0.5 s, for the Rust engine only.)

The cost transcript at `879eaa28` (`docs/evidence/issue-334/transcript.txt`) measured the worst patterns both budgets admitted at 256 positions, over a 65 536-character subject. The worst Rust call took about 1.1 s at the median: `a(?:\B[abc]){254}c` over Deseret letters. The worst RE2 call took about 0.8 s: `a[^\n]{254}c` over the same letters. Both are far over the 0.25 s that the decision above claimed.

The claim came from an estimate of about 1 s per MiB of subject at 256 positions, between the 4.2 s per MiB of `(?:a|b)[abc]{1000}(?:a|d)d` and the 200 ms per MiB of its `{30}` form. That estimate is wrong for a pattern that defeats both engines' lazy DFAs. Once the DFA gives up, Rust's Pike VM and RE2's NFA pay for every live position on every byte, so the cost per byte grows linearly with the positions. A subject of 4-byte characters is also four times as many bytes as characters. The transcript's sweep of Rust's slowest family showed the linear growth: about 0.23 s per call at a repeat count of 64 and about 0.49 s at 128. RE2's slowest family cost about 0.26 s at 64.

At 64 positions, `[0-9a-f]{64}`, a UUID regex, `\d{1,3}(\.\d{1,3}){3}` and `(?:a|b)[abc]{30}(?:a|d)d` stay admitted. `(?:a|b)[abc]{1000}(?:a|d)d` and `[A-Za-z]{1000}` stay refused with a hint. Every character is a position, so a literal over 64 characters is refused too, and so is a `like` operand over 62, because the anchors its regex gains count as well (see below). A `like` or `ilike` operand can therefore no longer reach the 1024-byte length cap: 62 four-byte characters are 248 bytes. A glob class is one position, so a glob still can.

The transcript rerun at 64 positions replaces the one at `879eaa28` and checks every admitted case against the 0.4 s ceiling.

### Every compiled node counts toward the repeat budget

Review of the first pull request found the budget counted only atoms, so a pattern could hide its cost in nodes that match no character. Once both lazy DFAs give up, Rust's Pike VM and RE2's NFA step through every instruction such a node compiles to, on every byte. Over a 65 536-character subject, at 64 positions or fewer, each of these took over a second a call in Rust:

- eight `\B` before each of 62 classes (about 1.1 s; 32 `\B` took about 4.2 s);
- 490 empty capture groups before 32 positions (about 1.2 s), and capture groups nested around an atom the same way. RE2 pays for capture groups too;
- 64 empty alternations, `(?:|)`, in each of 62 units (about 1.1 s), and 128 repeats of nothing, `(?:)?` (about 2.2 s).

So within the 64-position ruling, every node that compiles to an instruction counts at least one position, multiplied by its enclosing counted repeats like an atom: every assertion (`^`, `$`, `\A`, `\z` and every word boundary), every capture group, named or not, an alternation branch that holds no position, each `|` of an alternation, a repeat's operand that holds none, and each repeat itself. Only nodes that compile to no instruction count zero: flags, empty groups in a concatenation, a non-capturing group itself and a concatenation itself. A timed probe shows the first three free. `(?x)` whitespace and comments are not nodes at all. The walk matches every syntax-tree variant without a wildcard, so a `regex-syntax` release that adds one fails to compile until someone prices it. `(?:\B\B\B\B\B\B\B\B[x]){62}` is now 558 positions, and the 490-group pattern 523. Each is refused. The 490-group pattern also opens with a `\B`, so it counts 1 + 490 + 32 = 523, not 490 + 32.

A repeat counts `max(upper × operand, operand + 1)`. `operand` is what the operand holds, and an operand that holds no position counts one. `upper` is the most times the repeat can match: 1 for `?`, `n` for `{n}` and `{m,n}`, and for an unbounded repeat its lower bound plus one, so 1 for `*`, 2 for `+` and `m + 1` for `{m,}`. The `operand + 1` is the floor inside the `max`, not an addition: the split a repeat compiles to makes it count at least one more than its operand, and a count of two or more already multiplies past that, so `x{3}` is 3, not 4. A second review found why the repeat must count on its own: a repeat whose upper bound is one, `?` or `*`, added nothing once its operand held a position, so wrappers nested for free. 120 `(?:…)*` wrappers around a 4-byte class, counted 62 times after a `\B`, were priced at 64 positions, and one call over 65 536 Deseret letters took 4.5 to 5.2 s in Rust, or about 2.4 s with `?`. Now `x?`, `x*`, `x{0,1}` and `x{1}` are two positions, each nested wrapper adds at least one, and that pattern is 7504 positions. `\w{20}`, `[0-9a-f]{64}` and `x+` keep their counts, and every ordinary pattern above stays admitted.

An alternation counts one position for each branch after the first, on top of what its branches hold, because `n` branches compile to `n - 1` splits. A third review found that the walk counted only the branches, so an enclosing repeat copied splits that cost nothing. Four branches of `\pL` that counted 1, 2, 4 and 5 positions, under `{0,2}`, inside 38 `(?:…)?` wrappers, between `\B` and `\PL`, were priced at 64 positions. Over 65 536 Deseret letters one `DuckDB` call took about 450 ms, over the 0.4 s ceiling. Now `a|b` is 3 positions, `a|b|c` is 5, `(?:a|)` is 3 and `(?:a|b){3}` is 9, and that pattern is 70 and refused. A concatenation still adds nothing of its own, because it compiles to no instruction.

The anchors a `like`, `ilike` or glob translation adds are two positions, so such an operand holds 62 characters. A `%`, or a glob's `*`, translates to `.*`, which is two positions. The ordinary patterns above stay admitted. The access-log parser in the calibration corpus, with its anchor, its ten groups and its one `|`, is 61 positions. The cost transcript adds a family for each charged node kind and one of the zero-charge nodes, which must cost what the same repeat costs without them, and families of nested repeats outside any count and inside one.

### The batch `extract` reads named groups among themselves

`DuckDB`'s scalar `regexp_extract` reads one group by index, and only indices 0 to 9. With absolute indices, a named group inside or after nine unnamed groups read index 10, and an admitted `extract` failed in batch while the live lane, reading by name, answered. So the batch lane binds a copy of the body with every unnamed group made non-capturing, rewritten on the syntax tree and printed back, and reads each named group by its place among the named groups, from 1. A group's kind never changes what a regex matches, so all three lanes still read the same text. The emit-time counter charges the rewritten body's bytes. A body of ten or more named groups still reads index 10 and fails in batch with `DuckDB`'s own message, as it did before this decision. (Amended 2026-11-04, later: the batch lane reads every named group from one struct-form `regexp_extract`, so a body of any number of named groups works in batch. See that amendment.)

## Amendment (2026-11-04): what the limits bound in each engine

Human rulings of 2026-11-03 and 2026-11-04. They refuse two class forms, cap what the batch engine compiles, set the ceiling on one call at 0.5 s for the Rust engine only, and accept one residual risk in the batch lane until 1.1. Every limit keeps the value it has: 64 positions, 2^24 translation units, a 1 MiB program, a 512 KiB batch view and a 1024-byte body. No further pricing rule is added.

### Nested classes and class set operators are refused (2026-11-03)

DuckDB's RE2 reads a class nested in a bracketed class, and the operators `&&`, `--` and `~~`, as plain characters. The first `]` closes the class, and every operand joins one union. So `[\pL&&a]` matches `a` in the live lane and any letter or `&` in the batch lane, which breaks the parity ADR-0001 requires. One position of the repeat walk could also hide several RE2 classes: FIX6 measured admitted bodies of 9.6 to 377 KiB that cost 0.40 to 0.94 s a DuckDB call.

Every regex body is checked on its syntax tree after the length cap: a search `/re/`, a quoted or regex-literal `matches` and an `extract` body. A body that nests a class or uses a set operator is a parse error, `nested character classes and the class set operators &&, -- and ~~ are not supported`. A flat class holds the same characters. An escaped `[`, `]`, `&`, `-` or `~` and a POSIX class such as `[[:alpha:]]` stay admitted. ADR-0001's dialect difference, Unicode `\w`, `\d` and `\s` in Rust against ASCII in RE2, is unchanged.

### The batch engine's view of a body is capped at 512 KiB (2026-11-03)

DuckDB binds `regexp_matches` with RE2's default options, so `max_mem` is 8 MiB and the forward program gets two thirds of it. RE2 sizes its DFA from what the program leaves. `PartialMatch` runs the longest-match DFA at half of that memory, with one mark for each instruction, and the DFA's constructor fails when the state budget left holds fewer than 20 states. After a failed init, every call runs the NFA. That budget predicts the measured step exactly. `\B(?:\pL?){14}\PL` compiles to 17 918 RE2 instructions, keeps its DFA and takes 0.5 ms a call. `{15}` compiles to 19 112, fails init and takes 452 ms. Across the large-class families, init fails between 18 230 instructions, still a DFA, and 18 914.

The repeat budget cannot see this step: `\pL` is one position and a large program. Trawl cannot read RE2's instruction count, so it measures a view instead. The view is the body with `\w`, `\d`, `\s`, `\b` and `\B` rewritten on the syntax tree to their RE2 ASCII meanings (`pattern/re2.rs`), compiled by the `regex` crate. (Amended 2026-11-04, later: compiled by the owner's one meta-engine build, under the same NFA size measure as the `regex` crate's `size_limit`.) On the view, the step lies between 628.7 KiB, the largest view still in DFA mode (`\B(?:\pL?){14}\PL`), and 663.9 KiB, the smallest one past it (`\B(?:(?:\pL|\pN|\pS)?){12}\PL`). The cap is 512 KiB, 18.6 % under the first and 22.9 % under the second. A body over it is a parse error, `regex pattern too large for the batch engine once compiled (max 512 KiB)`. `\pL{12}` fits and `\pL{13}` does not. `\w{20}` fits both caps, because its view is ASCII. A glob, `like` or `ilike` operand never reaches RE2, so only the 1 MiB cap applies to it. The cost transcript's RE2 step part records the families on both sides of the step.

The cap keeps RE2's DFA alive at init. It does not bound one RE2 call once the DFA gives up on a busy subject, which the next section records.

### The ceiling on one call is 0.5 s, in the Rust engine only (2026-11-04)

FIX9 searched composed shapes at the edge of every limit and found admitted bodies that reach the 0.4 s ceiling of the 2026-11-03 amendment in Rust. Its worst is `a(?:\BF{0,2}){14}(?:F{0,2}){10}[^abc]`. Here F is FIX7's fan class, which holds one code point for each UTF-8 lead byte and for each continuation byte along the subject's path, so every list of byte ranges the subject walks through is long. `a`, `b` and `c` stand for U+FFFD, U+FFFC and U+FFFB, and the subject is 65 536 of them, eight tenths `a`. Once the lazy DFA gives up, the Pike VM in regex-automata 0.4.16 scans each sorted list from its start on every byte, so bytes that sort late, such as the `EF BF xx` of these characters, cost the most. FIX9 measured 394 to 398 ms at the median at a 1-minute load average of 5 to 5.5, and up to 404 ms for one call.

The human set the ceiling at 0.5 s and kept every cap. It applies to the `regex` crate, which runs the live lane and the batch `extract kv` tail. The cost transcript, `docs/evidence/issue-334/transcript.txt` at `eeff3681`, fails if any call it makes to an admitted shape, `is_match` or captures, takes 0.5 s or more. It passes. Its slowest screened call took 400.44 ms. In the full timing, the slowest median was 398.71 ms, FIX9's shape. Its slowest call was 402.90 ms, `a(?:\BF{0,2}){16}(?:F{0,2}){7}[^abc]` over the same subject. The 1-minute load average was 2.88 at the start of the part and 1.97 at its end.

DuckDB's RE2 gets a measured envelope with no ceiling (2026-11-04). The same transcript's slowest RE2 call was `a(?:\BF{0,2}){12}(?:F{0,2}){12}[^abc]` over the same subject: 1762.37 ms at the median and 1768.47 ms at most, at a load average of 1.87 rising to 4.55. FIX9 measured 1836 ms for its own shape. So one call over one capped value costs at most 0.5 s in Rust and about 1.8 s, measured but not asserted, in RE2.

### A timed-out batch regex can keep its slot past its deadline (residual risk)

DuckDB checks for an interrupt only between the 2048-row vectors it filters, never inside the regex calls over one vector. A `/query` that times out answers at its deadline, and ADR-0024 keeps its executor permit until the physical work stops. So the permit stays held until each of the query's DuckDB threads, 4 by default, finishes its vector. The slot shows as retained work (`pool_retained`, ADR-0024) for that time.

`docs/evidence/issue-334/cancel-overhang.txt`, pinned at `92f14aa9`, measures this through trawl-server's executor pool with one permit and a 5 s deadline. The probe and its corpus generator are in `scripts/evidence/issue-334/cancel-probe/`, and `scripts/evidence/issue-334/cancel.sh` reruns it.

- `漢[漢字文]{62}[^漢字文]` over 65 536-character CJK values, 4 files of 2048 rows: the request answered at 5.001 s, and the permit was free at 188.640 s, 183.6 s after the deadline.
- `漢F{48}[^漢字文]`, F the fan class, over 2048-character values, 8 files of 4096 rows: the permit was free 102.2 s after the deadline.
- FIX8 ran the fan body over 65 536-character values. The permit was still held 535 s after the deadline when the observation stopped. At 1.13 s a call, one vector is about 39 minutes on one thread, and about 44 minutes at the slowdown measured under 4 threads. At the RE2 envelope above, 2048 calls take about 60 minutes.

Threat model. The actor is an authenticated user with query rights. The data is stored values near the ingest cap of 65 536 characters, whether a sender wrote them on purpose or they occur in the logs. Each such query holds one executor slot and its DuckDB threads for up to about an hour after it has answered. Enough of them hold every one of `max_concurrent_queries` slots, one per CPU and at most 8 by default. Every other lane that reads Parquet then waits for a slot and times out at its own deadline, and work that needs the whole pool, such as a repin cutover, is blocked. The code before this decision has the same overhang with no bound: it had no repeat budget and no field cap, so one call over a stored value could cost tens of seconds, and a vector 2048 times that.

The human ruled that 1.0 ships with the overhang documented as a known limitation in the release notes. The fix is deferred to 1.1: batch regex work checks the query's cancellation latch between rows, not between vectors. Until then, the batch lane's unit that cannot be stopped is the rest of one vector on each query thread, not one call.

### The emit-time counter charges a pivot's fill (2026-11-04, later)

ADR-0062 gives a dynamic pivot a fill when a later stage reads a name the pivot's keys do not cover. The fill is a zero-row select that repeats the aggregate, so `DuckDB` binds every regex in the aggregate once more. The counter charged a pivot aggregate at `pivot_filter_threshold` copies, 20, and missed this one: 16 search regexes and 12 aggregate patterns, followed by `| where zzz > 0`, bound 268 `regexp_matches` calls and were admitted. The counter now charges one more copy of the aggregate's patterns, in count and bytes, when the fill takes its first name. No earlier point knows whether the fill renders. The charge comes before the fill joins the statement, so a refused query never reaches `DuckDB`. A pivot that no later stage pads is charged as before.

## Amendment (2026-11-04, later): the regex memory bounds

The second pull request (#335) calibrated the memory bounds of the decision above. Two human rulings of 2026-11-04 changed the decision: DuckDB's RE2 counts in the server-wide reservation, and its allowance is set by kind of site, with one RE2 for each `extract`. This section records the values that ship and the measurements behind them. The transcripts are in `docs/evidence/issue-335/`. The paragraphs above that these values change carry a note that points here.

### The backing

`Pattern` is backed by the meta engine of `regex-automata` 0.4.16. The root `Cargo.toml` pins that exact version, because the charge formula below follows the engine's internals. Each prepared pattern owns one cache behind a lock, and every clone of the pattern shares it. No search uses the engine's implicit `Pool`. A clippy rule bans that type and the meta search methods that take a cache from it, outside the owner module, and the construction inventory counts the `regex-automata` builders. The reason is accounting. A pooled cache exists once for each thread that searches, up to nine for each regex, so no bound per query can count it. An owned cache exists once, and the build can charge its bytes before any match runs.

Every pattern builds with the `regex` crate's syntax configuration and two engines turned off:

- **`dfa(false)`.** `tracing-subscriber` turns on the `dfa-build` feature of `regex-automata` in trawl-server, but not in trawl-core alone. With the full DFA on, one pattern would build and charge differently in each crate.
- **`backtrack(false)`.** The bounded backtracker's visited set and frame stack have no bound that the charge can count. Captures therefore run on the Pike VM or the one-pass DFA. `throughput.txt`, at `d2783798`, measures the cost against main's `regex` crate over the `log_regexes` corpus. `is_match` is at most 1.09 times as slow. Captures are at most 1.38 times as slow for the whole `extract` stage, and 1.44 times net of the row conversion, both for `(?P<key>\w+)=(?P<val>"[^"]*"|\S+)` over Unicode lines. The human accepted this cost.

### What a pattern charges

The build computes a pattern's charge once, from integers it reads off the pattern's forward NFA and its program, so no clock and no hash order enter it (`pattern/charge.rs`). The charge is the program, three lazy-DFA caches at twice their capacity, the Pike VM's scratch and the capture slots. A lazy DFA's heap can pass its capacity, because a clear frees nothing; the peak measured is 1.62 times the capacity, so 2 leaves a margin of 23 %. A pattern is charged for three lazy DFAs, forward, reverse and the reverse prefix of the `ReverseInner` strategy, whatever strategy meta picks.

**Cache capacity** is `clamp(6 × the forward lazy-DFA minimum, 16 KiB, 2 MiB)`. Over the corpus and the Unicode table, the largest reverse minimum is 5.10 times the forward one, so 6 keeps every lazy DFA on. `pattern::tests::lazy_dfa_stays_enabled` proves this for every pattern in `log_regexes`. 2 MiB is the `regex` crate's default, so no pattern gets a larger cache than it had before. The decision above says capacity "derives from that budget". The orchestrator's ruling reads that as follows: each pattern's capacity follows from its own minimum, and the budget refuses what does not fit. A capacity never grows into budget that its query leaves unused. Otherwise every query would hold its whole budget, and fewer streams could run at once.

### The per-query budget

`REGEX_QUERY_BUDGET` is 32 MiB, not the 16 MiB candidate, with no config key. A query is admitted while the sum of its patterns' charges plus one build transient of 4 MiB fits. A ledger builds one pattern at a time, so one transient covers all its builds. The worst transient measured is 2.25 MiB. At 32 MiB the whole `log_regexes` corpus fits one query, and so do three patterns near the 1 MiB compiled-size limit, such as `\w{20}` at about 7.3 MiB each. A fourth does not. The first build over the budget is refused with 503 `query_resource_exhausted` and the cause `regex_budget_exhausted`. `pattern::tests::query_budget_exact_and_one_over` proves that a budget equal to the sum is admitted and one byte less is refused.

`parse` and `/validate` build each pattern through the same build function in a check mode. That mode drops the program at once, holds no cache and takes no reservation, so validation and matching cannot accept different patterns. Its transient is at most 4 MiB for each parse in progress.

### The server-wide reservation

`REGEX_RESERVATION_BYTES` is 1.25 GiB, not the 256 MiB candidate. `QUERY_RESERVATION_CAP` is 512 MiB: one query may hold at most that much of the reservation, its pattern charges and its RE2 allowance together. Neither has a config key (`pattern/memory.rs`).

- **Live lane.** A metered build holds one transient before it builds, then resizes the hold to the pattern's charge. The pattern owns the hold, and the bytes return when its last clone drops. An SSE stream holds its patterns for its whole life.
- **Batch lane.** A batch query holds its RE2 allowance (below) before DuckDB binds its first regex. The hold lasts for the physical work, inside the executor's work closure, so a request past its deadline keeps it until the work ends. The `extract kv` tail charges its patterns through a metered ledger, too.
- **Refusals.** A query that needs more than 512 MiB can never run, and is refused with the cause `regex_budget_exhausted`. A query that does not fit beside what others hold now is refused with `regex_reservation_exhausted`. Both answer 503 `query_resource_exhausted` with the fixed sentence and no `Retry-After`. The cause is in the `http_failure` event, not on the wire. Nothing waits for bytes to come back: first come, first served.

The human ruled the size (1.25 GiB, corrected from a 1 GiB candidate). The bar is the most queries the `max_concurrent_queries` default runs at once, eight, each an ordinary search of five corpus patterns on four threads. Each holds 5 × 4 × 6.88 MiB = 137.6 MiB of RE2 allowance, so eight hold 1.1 GiB, and about 179 MiB is left for live streams. With a `sev()` read and filtered on in each, each holds about 140.5 MiB, and about 156 MiB is left. The bar holds beside a hot buffer too. Each search's filter runs in both branches of the hot+cold union, but a thread runs one branch at a time, so the search is still 5 sites (see the emitter's own regexes, below). With the hot branch's `_severity` conform each holds about 144.6 MiB, and about 123 MiB is left. With the `sev()` each holds 147.5 MiB, and about 100 MiB is left.

### DuckDB's RE2 counts in the reservation (human ruling, 2026-11-04)

`re2-memory.txt`, at `1f86b2cb`, measured the batch lane's worst case before this ruling: eight queries of 256 patterns on four threads gave RE2 6602.9 MiB of resident memory at the median (6682.5 MiB at most). `query_memory_limit` does not see it. Under a 64 MiB `memory_limit`, a query passed while RE2 grew by 2263.4 MiB, and `duckdb_memory()` grew by 0.7 MiB. That worst case alone is about 6.45 GiB of the 8 GiB process ceiling, and with the ledger's other rows it passes the ceiling. The human ruled that RE2 counts in the same server-wide reservation as the live lane. This replaces the measured envelope as a residual risk, which the decision above accepted.

The unit is one regex call that DuckDB binds or runs, counted over the finished statement with every copy its parser, binder and optimizer can make: the query's own patterns and the regexes the emitter writes itself (below). Each kind of the query's own patterns is never below the emit-time counter's count, lateral and pivot copies included. A query's allowance is each site at its kind's figure, once on each of its `query_threads`. The figures are set by kind of site, in a second human ruling. The transcript showed that a site's RE2 memory does not follow the size of its batch view, so a size-based allowance was rejected.

| kind | constant | allowance a site a thread | worst measured |
|---|---|---|---|
| `regexp_matches`, and every other site that is not an `extract` | `MATCH_SITE_RE2_BYTES` | 7046 KiB (6.88 MiB) | 5.50 MiB |
| `regexp_extract` | `EXTRACT_SITE_RE2_BYTES` | 13702 KiB (13.38 MiB) | 10.66 MiB |
| a regex the emitter writes itself | `FIXED_SITE_RE2_BYTES` | 9 KiB | 6.6 KiB |

Each figure is the worst measured over bodies at the full 1024-byte limit and the 512 KiB view, on 1 and 4 threads, with a margin of 25 % (`re2-memory.txt`, parts `SITE_SIZE` and `ALLOWANCE`). RE2 has a ceiling for each regex because DuckDB never changes RE2's 8 MiB default `max_mem`. RE2 gives two thirds of it to the forward program and one third to the reverse program. A match answers from the forward program. An `extract` must find where the match starts, so RE2 builds the reverse program too, and the extract figure is about twice the match figure. The figures are measurements with a margin. RE2 does not enforce them for a site as a whole, because each DuckDB thread compiles its own RE2 and the bind compiles one more.

### The emitter's own regexes (human ruling, 2026-11-04)

The final security review found regex calls the allowance did not count. The emitter writes four regexes with patterns of its own (`conform.rs`'s `FIXED_REGEXES`): the severity reading's two whitespace trims, its digits guard and its ASCII gate. `sev()` carries them, and so does a hot branch that conforms a `SEVERITY` pin, `_severity` whenever the hot buffer carries it. So a query of 1000 `sev()` calls bound 41 000 regex calls with no allowance. The human ruled that every such call counts, at a measured size. `re2-memory.txt`, part `FIXED_SITES` at `676a463d`, measured 512 and 2048 sites of each pattern on 1 and 4 threads over rows built to grow its DFA. The worst median was 6.6 KiB a site a thread, the trailing trim, and the largest single run 18.2 KiB. With 25 %, rounded up, `FIXED_SITE_RE2_BYTES` is 9 KiB. DuckDB copies these calls far past their text: `sev()` writes 4 and binds 41, because a simple `CASE` copies its subject for each arm. The binder copies lateral aliases, macro arguments, `BETWEEN` operands and `PIVOT` aggregates, and the optimizer substitutes a projection into a filter, copies a filter into each branch of a union, and can rewrite a window into a join of its input with an aggregate of it, which runs the input twice and copies a filter above into both sides. So the emitter counts them over the finished statement, as an upper bound on both plans (`emitter/regex_calls.rs`). `crates/trawl-engine/tests/fixed_regex_sites.rs` holds the count at or above DuckDB's bound and optimized plans over every shape, and holds its macro and function tables against the bundled catalog. Three `sev()` calls hold 123 calls, 4.3 MiB on four threads. A hot branch conforming `_severity` holds 199, 7.0 MiB. 1000 `sev()` calls need 41 000, 1.4 GiB, and are refused with `regex_budget_exhausted` before they hold anything. The optimizer copies the query's own patterns the same way: a filter on a `let` of `matches` runs one `matches` twice, a hot `matches` runs in both branches of the union, and a filter above a window runs in both sides of the join. A thread holds one branch of a union at a time, so a union counts its heaviest branch, kind by kind. Each branch is a pipeline of its own, and a pipeline task builds the expression state that holds a call's RE2 on its first run and drops it when it finishes; `emitter/regex_calls.rs` cites the DuckDB source. `re2-memory.txt`, part `UNION_BRANCHES` at `09366e7b`, measured a union of two branches against one scan of the same rows: 1.07 to 1.16 times the scan's RE2 memory at 4 and 16 sites on 1 and 4 threads, where both branches at once would be about 2. A join, an `EXCEPT` and an `INTERSECT` still count both sides. So the same count covers them, split by kind: `fixed` for a call of one of conform's regexes through its own function, `extract` for any other `regexp_extract`, and `matching` for the rest. Each parameter kind takes the larger of the emit-time count and this one, so no charge drops below the emit-time count, which still feeds the 256-pattern cap. A projection that names a column reads it, so it pays only its own calls and the aliases the binder copies in, and a 40-group `extract` stays one site. The hot branch is charged its whole conform, 199 fixed calls, about 7 MiB a query on four threads, for each `SEVERITY` pin, even for a `count()` that reads no severity: an over-count that breaks the eight-query bar at four pins, or three with a `sev()` filtered on, left for a follow-up.

### One RE2 for each `extract` (human ruling, 2026-11-04)

The batch lane binds an `extract` body once, as one struct-form `regexp_extract(source, ?, ?::VARCHAR[])`. The second parameter is the list of field names `[g1, …, gn]`, bound as a parameter that is not a regex. An inner stage computes the struct once a row. The outer stage reads each named group from its field through `nullif(…, '')`, so a group that took no part in the match, and every group of a row that does not match, reads as NULL, as in the live lane. The body binds with its unnamed groups made non-capturing, as the amendment of 2026-11-03 rules, so named group k is field k.

The names list is bound because DuckDB's struct form needs a constant pattern when it binds the call. A statement prepares before its values are bound, so a bound pattern is no constant at prepare, and a literal names list beside a bound pattern is refused. A bound names list defers the bind until the values are bound, and the pattern is then a constant (`crates/trawl-engine/tests/extract_struct.rs`).

So an `extract` stage is one site and one RE2 a thread, whatever its group count, and the limit of nine named groups is gone. A filter on one of its fields is the exception: the optimizer substitutes the call into the filter, twice through `nullif`, so the stage is three sites, counted with the optimizer's copies above. The addendum to `re2-memory.txt` measured one extract of 40 named groups. As 40 scalar calls, it held 110.4 MiB on one thread. As the emitted struct form, it held 8.76 MiB a site on one thread and 4.50 MiB on four, within the 13.38 MiB allowance. An `extract` still charges one for each named group toward `MAX_QUERY_PATTERNS`; this amendment does not change that charge.

### What the bounds cost

- **The 0.5 s ceiling holds.** `cost-recheck.txt`, at `35ab3258`, reran the first pull request's Rust cost gate at this backing. The slowest median was 394.97 ms and the slowest call 398.38 ms. Part one measured 398.71 ms and 402.90 ms.
- **Admission is slower.** The costliest admission, 256 distinct patterns near the compiled-size limit, took 1801.15 ms at the median, 7.04 ms a build, against 1232.38 ms at part one: 46 % more. Each build now compiles the forward NFA for its profile before it compiles the program.
- **Resident memory stays within the reservation.** `rss.txt`, at `561fde38`, ran 32 live streams, each of `\w{20}`, `(?i)\w{20}`, `\pL{12}` and an address pattern, then eight batch queries at once, each needing a 495.4 MiB RE2 allowance. One query ran and seven were refused with `regex_reservation_exhausted`. Of two more heavy streams opened while that query ran, the second was refused the same way. Peak resident growth over the idle baseline was 371.6 MiB, within the 1280 MiB reservation. Five seconds after the streams closed, growth was 31.4 MiB.

ADR-0056's memory arithmetic gains the reservation row and the RE2 line in its amendment of the same date.
