## Reading

The test parks four junk-token HEAD /api/v1/queries requests in verify_key behind
LOCK TABLE api_keys. At the parent those four fill the one control allowance, so the
first probe, GET /api/v1/health, is refused before its handler with 503
request_limit_reached and the control message. That is the starvation #298 describes:
a caller with no valid key fills the reserve that liveness and readiness depend on.
The readiness wait reads Postgres and the in-process gauge, not /metrics, so the first
failing assertion is health's, not a scrape's.
