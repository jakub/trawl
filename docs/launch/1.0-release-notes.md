# Initial-release notes, draft

Status: unpublished contributor draft for the chosen Trawl 1.0 launch contract.
The support decisions are settled; the final release identity, artifact
verification, and publication remain pending in the readiness ledger.

## Current capabilities

Trawl collects and searches logs for homelabs and small installations on one
node. It stores events in Parquet and executes a pipeline query language with
DuckDB. The browser, CLI, and terminal UI provide access to server queries.
The CLI can also query local Parquet files without a server.

The current implementation provides these capabilities:

- HTTP ingest and optional native syslog listeners, with Vector integration examples.
- Filters, aggregations, field inspection, live queries, and result export.
- Saved query text, scheduled reports, and stored run results. A saved query does
  not freeze its current results.
- Role-based access through Fleet keys and browser sessions.
- A field catalog, retention controls, health metrics, and backup and recovery procedures.

These statements describe the prepared source. The selected release must pass
the recorded artifact checks before these notes become its announcement.

## Requirements and limits

A server installation needs persistent storage and PostgreSQL for the Fleet
keystore and Trawl app-state databases. `trawld` owns ingest, storage, queries,
and the HTTPS API. `trawl-web` serves the browser UI and requires an API
connection, a public origin, and a persistent session key. Clients need
credentials with the required permissions and trust in the server TLS certificate.

Trawl has no clustering, sharding, or multi-tenancy. There is no published
hardware minimum or general throughput guarantee. Memory and storage needs
depend on the ingest rate, retention window, and queries. A single-node
installation needs its own backup and restore plan.

The repository contains Debian packaging, Linux archives, container and Helm
deployment paths, and source-build instructions. The final supported channel
and platform list needs release verification. Packaging code alone does not
prove that an artifact installs or runs on a clean host.

## Chosen launch contract

The launch uses fresh Trawl application state and a fresh shared Fleet keystore.
Coastwatch will be anchored to the resulting Trawl revision after both consumers
are verified. Existing installations are not reset or converted automatically.
[ADR-0032](../adr/0032-fresh-state-launch-baseline.md) records this decision;
implementation and verification remain tracked in the readiness ledger. The
platform target is a Linux server plus a macOS CLI. The chart will support
optional cert-manager Certificate creation as well as an existing TLS Secret.
These chosen targets still require their recorded verification before publication.

Source and release artifacts will be public. Their visibility and anonymous
installation paths must be verified after publication is authorized. The
[readiness ledger](1.0-readiness.md) tracks implementation, review, and evidence
for each chosen contract; no choice authorizes changing an existing installation.

## Release coherence required before publication

Select one release commit for the stable manual, binaries, container image,
Helm chart, and shipped examples. Record the final versions and artifact
identities, then verify installation through each supported channel. Confirm
that the stable manual describes those exact artifacts and that development
documentation remains identified separately.

The prepared Docs workflow builds the stable manual at the release resolver's
exact product commit and records that identity in `release.json`. Main and
pull-request builds remain labeled development artifacts. Release publication
must gate stable-site deployment; live publication has not been exercised.

Before these notes become an announcement, record the verified release identity
