fleet is a self-hosted log collection, storage, and search platform designed for homelabs and small-to-medium infrastructure. it combines Vector for log ingestion, Apache Parquet for compressed columnar storage, DuckDB for analytical query execution, and a custom domain-specific query language inspired by Splunk's SPL — delivering a Splunk-like search experience at zero licensing cost and minimal operational complexity. the entire system runs comfortably on a single machine, handling tens of billions of log events before architectural limits require attention. the core thesis is that modern storage formats and embedded analytical databases have made single-node log search viable at scales that previously demanded distributed clusters, and the industry's push toward complexity serves vendor revenue more than user needs.

the project's primary goal is a fast, ergonomic log search experience accessible through three frontends: a terminal UI for ssh-based investigation during incidents, a web interface (Rails) for day-to-day exploration and dashboards, and a CLI tool for scriptable queries and unix pipeline integration. all three frontends are thin presentation layers backed by a single Rust daemon (fleetd) that owns query parsing, planning, execution, authentication, retention management, and schema introspection. the query language is pipeline-oriented — users start with intuitive search syntax (service:nginx level:error last:2h) and progressively refine with pipe stages (| stats count() by host | where count > 10 | sort -count) that compile to optimized DuckDB SQL behind the scenes. the language prioritizes the operations people actually perform during log analysis: filtering, aggregation, time-series bucketing, field extraction, and frequency analysis.

beyond log search, the platform includes a lightweight fleet management capability through a signed-template agent architecture. a small Rust agent binary deployed to managed endpoints checks in with the central daemon, receives cryptographically signed task definitions (shell commands, package inventories, system stats, config deployments), executes them within locally-enforced security constraints, and reports results through the same Vector log pipeline. task templates are signed offline with ed25519 keys (supporting file-based keys, YubiKey PIV, and FIDO2 passkeys) and embed explicit constraints — targeting rules, validity windows, execution limits, command allowlists, and parameter schemas — that the agent enforces independently of the server. this means even a fully compromised server cannot create novel execution authority; it can only dispatch pre-approved, operator-signed templates. server-side playbooks chain templates together for automated investigation and remediation workflows, with human-in-the-loop approval gates for dangerous actions.

the scope is deliberately bounded to single-node operation. there is no clustering, sharding, replication, or multi-tenancy. authentication uses API keys with three roles (admin, analyst, reader) stored in an embedded SQLite database, and agent authentication uses mutual TLS with an internal certificate authority. the system targets a sustained ingest rate of 20–50k events per second, 1–5 TB of compressed storage with automatic retention management, sub-second query latency for filtered recent searches, and 3–5 concurrent heavy analytical queries on an 8-core machine. these numbers cover the vast majority of homelab and SMB deployments. the architecture does not preclude future scaling work, but it is not designed for it and no current decisions optimize for distributed operation.

the implementation is structured as 15 phases over roughly 44 weeks at half-time effort, with every phase producing an independently useful artifact. a working CLI that queries parquet files arrives at week 9; the authenticated daemon with all three transports at week 16; the TUI at week 24; the web UI at week 28; and the complete agent and playbook system at week 42. the agent capability (phases 11–14) is treated as an optional v2 scope — the log search platform is complete and useful without it. the project is implemented as a Rust workspace with clean crate boundaries separating pure query logic (no I/O dependencies, testable in isolation, potentially compilable to WASM) from the database engine, authentication, and network transport layers. the web UI is a separate Rails application communicating with the daemon over HTTP, and the TUI is a separate Rust binary using the shared client library.
