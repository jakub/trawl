# Trawl 1.0

Trawl collects and searches logs for homelabs and small installations. Run one
Linux server, send it events over HTTP or syslog, and search them from a browser,
the command line, or the terminal UI. Events are stored in Parquet. The CLI can
also query local Parquet files without a server.

Start with [your first query](https://trawl.sh/getting-started/first-query/):
on a Linux machine with Docker, `trawl trial up` starts a disposable trial with
sample data, and the tutorial checks the same result in the browser and the
CLI. The [installation guide](https://trawl.sh/getting-started/) covers the
server packages. If someone already operates Trawl for you,
[connect to their server](https://trawl.sh/start/connect/).

## What you can do

- Collect application and system logs with HTTP, native syslog, or the supplied
  Vector configurations.
- Filter events, inspect fields, calculate aggregates, watch live results, and
  export results to Parquet.
- Save query text for reuse or schedule reports that keep their run results.
  Saving a query does not freeze its current results.
- Control access with API keys, roles, and browser sessions.
- Manage field types, retention, health checks, and backups on one server.

## Installation choices

| Platform | Available components |
| --- | --- |
| Linux amd64 and arm64 | Server and CLI archives, Debian packages, and container images |
| macOS 15 or newer, Apple silicon and Intel | CLI archives |
| Kubernetes | Helm chart for the Linux server and browser |

Linux packages are verified on Debian 12. Archives include the DuckDB runtime;
keep their `bin/` and `lib/trawl/` directories together. macOS archives use
ad-hoc signatures and are not Apple Developer ID signed or notarized. See the
installation guide for prerequisites and first-run approval.

The Helm chart can use an operator-supplied TLS Secret or request a Certificate
from an installed cert-manager issuer. The
[deployment guide](https://trawl.sh/operate/deployment/) covers both paths.

## Requirements and scope

A server needs persistent storage and PostgreSQL, with separate databases for
authentication and application state. Clients need an API key with the required
permissions and trust in the server's TLS certificate. The browser requires
its own public origin and persistent session key.

Trawl is designed for one node. It does not provide clustering, sharding, or
multi-tenancy. Storage and memory needs depend on ingest volume, retention,
and queries. Use the [backup and restore guide](https://trawl.sh/operate/backup-restore/)
to protect an installation.

## Upgrade notes

`trawl-web` now verifies trawld's certificate in every installation. It trusts
the platform roots or a pinned CA file, and the upstream must be `https`. On
first start it waits for trawld's generated certificate and answers 503
`upstream certificate not available` until the file exists. It loads a
replaced CA file within 30 seconds, with no restart. A new setting,
`[web] upstream_connect_addr`, lets it verify a DNS name in trawld's
certificate while it connects over loopback.

The Debian package pins trawld's generated certificate with
`[web] upstream_ca_path` in `/etc/trawl/trawld.toml`. That file is a conffile.
When you edited it, dpkg asks whether to keep your copy. Keeping it is the
default answer, and `--force-confold` keeps it without asking. A kept
`trawld.toml` does not get the new setting. Without it, `trawl-web` checks
trawld's self-signed certificate against the system roots, the check fails,
and every sign-in returns 502. After the upgrade:

1. If the `[web]` section of `/etc/trawl/trawld.toml` has no
   `upstream_ca_path` line, add this line under `[web]`:

   ```toml
   upstream_ca_path = "/var/lib/trawl/tls/cert.pem"
   ```

   trawld writes that certificate when `[server] tls_cert_path` is not set.
   If you moved `[data] path`, use `tls/cert.pem` in the parent directory of
   that path, where trawld writes the certificate instead.
   If you set your own `tls_cert_path`, use the file of the CA that issued it.
2. Run `sudo systemctl restart trawl-web`. Check that
   `systemctl status trawl-web` shows `active (running)`, then sign in.

The Helm chart pins trawld's certificate in every `tls.mode`. With
`web.enabled` in `secret` or `certManager` mode, set `tls.upstreamCa`, and
`tls.upstreamServerName` for `secret`, before `helm upgrade`. Without them the
render fails and names the value to set. The
[deployment guide](https://trawl.sh/operate/deployment/#configure-the-daemon-api-certificate)
shows each mode.

trawld keeps the private key of its generated certificate in `tls-key/`,
beside `tls/`. The first start after the upgrade deletes the old
`tls/key.pem` and generates a new certificate. A client that pinned the old
certificate needs a copy of the new one.

The syslog listener no longer reads an RFC 3164 timestamp that carries no
offset in the zone of the trawld host. It reads it in the new
`[syslog] default_timezone`, or in UTC when that is unset. The container image
already read UTC. On a Debian install whose host is not on UTC, and whose
senders log local time, set `default_timezone` to the senders' zone before
you restart trawld. Otherwise their new events land hours away from older
ones. `[syslog.sender_timezones]` sets the zone for one peer. The Helm values
are `config.syslog.defaultTimezone` and `config.syslog.senderTimezones`.

trawld now checks the syslog peer settings at startup even when the listener
is off. A `source_service_map` key that is not an IP address, and a malformed
`allow_cidrs` entry, now refuse to start. Before, such a key never matched a
peer, trawld dropped such an entry with a warning, and a list where every
entry was malformed accepted every peer. Run `trawld --check-config` before
you restart.
