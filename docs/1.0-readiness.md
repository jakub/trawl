# trawl 1.0 readiness assessment

## what we have (and it's genuinely solid)

**query language** — complete. full pipeline DSL with 14 pipe stages, 17 aggregation functions, 12 scalar functions, OR groups, time filters, regex/glob/kv extraction. parameterized SQL emission throughout — no injection vectors. `CompiledFilter` provides proven-equivalent in-memory matching for SSE (property-tested against DuckDB output).

**ingestion pipeline** — complete. ndjson/json ingest → WAL → hot buffer (visible to queries within ms) → hourly parquet compaction → daily rollup. event bus with broadcast channel for real-time streaming. retention with age-based + disk-pressure policies.

**server** — complete and well-hardened. axum with proper middleware stack (rate limiting per role, CORS, HSTS, concurrency limits, request IDs). TLS with auto-gen self-signed certs and hot-reload. prometheus metrics at `/metrics`. internal telemetry that feeds server ops back into its own pipeline (you can `service=trawld | stats count() by event_type` to monitor the daemon with itself).

**auth** — complete. argon2id hashed API keys, four roles with orthogonal permissions, SQLite-backed, LRU-cached lookups, timing-safe dummy hash for invalid tokens. `trawl-admin` CLI for offline key management.

**CLI** — complete. query/validate/embedded-mode, four output formats (table/json/csv/parquet), formula injection protection on CSV export.

**TUI** — complete and polished. multi-tab editor with syntax highlighting, schema browser with field profiling, query history, saved queries, live tail via SSE, vim-style result search, clipboard integration, driver mode for programmatic control.

**schedules/reports** — landed. cron-style periodic query execution with zstd-compressed result storage, crash recovery, atomic run tracking.

**testing** — genuinely good. ~100 emitter snapshots, filter/SQL parity property test, ~30 engine integration tests against fixture parquet, ~40 HTTP integration tests against real server instances, hot buffer pipeline end-to-end test.

**error handling** — mature. typed enums at every boundary with `thiserror`, span info on parse errors, error redaction before crossing trust boundaries.

## what's missing for 1.0

### must have (blocking)

**release & packaging** — biggest gap. zero packaging infrastructure right now.

- dockerfile (multi-stage, statically linked musl binary)
- github actions release workflow — cross-compile for `x86_64-linux-gnu`, `aarch64-linux-gnu`, `aarch64-apple-darwin`, publish to github releases
- systemd unit files for trawld (+ sysusers/tmpfiles for proper system integration)
- install script (`curl | sh` a la rustup) or at minimum clear build-from-source docs
- homebrew tap (nice but not strictly blocking)

**user-facing documentation** — CLAUDE.md is great for development but there's nothing for an actual user.

- getting started guide (install → first ingest → first query)
- DSL reference (the CLAUDE.md one is good, just needs to live somewhere discoverable)
- config reference (trawld.toml is well-commented but deserves a proper doc)
- vector integration cookbook (the config examples exist but need prose around them)
- API reference (the endpoint table needs request/response examples)

**upgrade/migration story** — what happens when someone on 0.9 upgrades to 1.0? parquet files should be fine (format is stable), but the SQLite auth DB schema might change.

- schema versioning in the auth DB
- migration runner (even a simple embedded one — rusqlite has this pattern)
- documented breaking change policy

**graceful degradation on data corruption** — what happens if a parquet file is corrupted? a WAL file is truncated? the auth DB is locked? right now these probably surface as DuckDB/rusqlite errors — need explicit handling and recovery guidance.

### should have (important but not blocking)

**alerting/webhooks** — scheduled reports are a great foundation, but the obvious next step is "when this condition fires, POST to a webhook / send to a slack channel." the scheduler infrastructure is already there; this is mostly a notification transport layer.

**S3/MinIO cold storage** — DuckDB's `httpfs` extension makes this relatively cheap to implement. for a homelab tool, "old logs go to a cheap NAS bucket" is a real use case. tier-1 improvement per the architecture review.

**config reload on SIGHUP** — TLS certs hot-reload already, but the rest of the config requires a restart. for a daemon that might run for months, SIGHUP reload is expected.

**cross-platform CI** — CI runs on ubuntu-latest only. the deny.toml targets `aarch64-apple-darwin` + `x86_64-unknown-linux-gnu`, so the intent is multi-platform, but there's no macos CI job. at minimum, test compilation on macos.

**cargo-fuzz / proptest** — the filter parity property test is great but the parser is the classic fuzz target. malformed DSL input → parser → no panics, no infinite loops. low effort, high value for a 1.0 confidence claim.

**coverage reporting** — `cargo-llvm-cov` in CI, even just as a metric. not as a gate, just visibility.

### nice to have (post-1.0 fine)

**web UI (rails)** — for a 1.0 targeted at homelabbers, the TUI is the primary interface and it's good. the rails app could come in 1.1 or later. people who want a web UI can use the HTTP API directly.

**agent system** (phases 11–14) — explicitly v2 scope and correctly deferred. signed task execution, mTLS enrollment, the whole trawl management angle — that's a different product surface.

**unix socket transport** — the plan mentioned this but HTTP works fine. not needed for 1.0.

**read-only query replicas** — cool idea from the architecture review, but single-node is the thesis. don't fight the thesis for 1.0.

**rustdoc publishing** — the code has doc comments but they're not deployed anywhere. useful for contributors but not for end users.

## meta-concerns

**naming** — "trawl" is an extremely common name. elastic's trawl, hashicorp trawl-related tooling, osquery trawl. for 1.0, check if `trawl` is taken on homebrew-core and docker hub, and consider whether the name collision matters for discoverability. (probably doesn't for a homelab tool, but worth a conscious decision.)

**MSRV vs security** — carrying a `RUSTSEC-2026-0009` ignore for the `time` crate because the fix needs rust 1.88 and MSRV is 1.85. for a 1.0, either bump the MSRV or pin a patched `time` version. shipping a known advisory is a bad look.

**`_max_rows` in scheduled queries** — accepted but unused. either wire it up or remove it before 1.0; dead parameters in public APIs are confusing.

## summary

the core is 1.0-quality code. the DSL, query engine, ingestion pipeline, auth, TUI — all solid, well-tested, properly error-handled. what's missing is everything *around* the code: packaging, docs, upgrade path, and a few operational niceties (alerting, cold storage, fuzz testing). the gap is "product readiness" not "engineering readiness."
