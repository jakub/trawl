# Trawl web UI inventory

Audit date: 2026-09-04 in America/Phoenix, 2026-09-05 UTC. Source commit: `a9628da7c73be7e397b83aeabbe5bd4f29787627`.

The web UI has a substantial working core. Search, History, Schema, Nets, and Runs are implemented pages with real server calls. It also has **13 visible placeholder entries or controls**, plus several broken or incomplete features inside the implemented pages. The most urgent repairs are the absolute time picker, visualization data handling, service cardinality, and stored-run navigation.

This is an inventory and browser audit. No product source was changed, no issue or PR was opened, and no changes were deployed.

## Evidence and environment

The configured dev URL, `https://fractal.reverse-manta.ts.net:8444/login`, returned HTTP 502. Ports 8081, 8090, and 5514 had no local listeners. I therefore built the current SPA and tested an isolated local stack with PostgreSQL, Fleet authentication, trawld, and trawl-web. The browser target was `http://127.0.0.1:18090`.

- SPA build: `env -u NO_COLOR trunk build --dist /tmp/trawl-ui-audit-20260904/dist`, run from `crates/trawl-web-ui`. Passed.
- Backend build: `CARGO_TARGET_DIR=/home/jakub/code/trawl/target/app-experiment cargo build --no-default-features -p trawl-server -p trawl-web`, run in a detached checkout of the audited commit. Passed. The runtime used private copies of those binaries.
- Initial data: 240 synthetic events, 80 each for nginx, payments, and auth. Later injections tested live delivery and differences between stored and current results. The fixture used an environment named `prod` inside the disposable database and data directory. It was not production data.
- Browser: T3 collaborative Chromium preview, primarily 1280 × 800. Narrow layout checks used 390 × 844. Both themes were inspected.
- The initial shell/placeholder checks used the repository's API stub at port 18123. Initial query and pagination checks used available older backend binaries. The backend was then rebuilt at the audited commit, and the main functional checks continued against the current real stack. Screenshots of placeholders use the current SPA regardless of backend.
- No existing dev database, service, user object, or credential was changed. Repin, pin deletion, and other corpus-changing administration were inspected in source, not executed.
- This was manual browser testing with source tracing, not an execution of the repository's Playwright regression suite, a full accessibility audit, or a complete server security review.

The preferred Browser runtime had no connected browser, and Chrome DevTools MCP could not acquire its shared profile. T3 preview provided the browser used for this audit. Neither error was treated as product behavior.

Screenshots and matching JSON files in this directory are the evidence. The JSON files contain visible page state and control descriptions. The later captures omit browser action history and authentication traffic. `exports.json` records the browser-created download blobs, not merely a successful HTTP request.

## Classification

| Class | Meaning |
|---|---|
| Browser verified | The described action completed against the real isolated backend, unless a row explicitly says stub or initial backend. This does not certify every edge case. |
| Source implemented | A concrete component and server operation exist, but that action was not executed in this audit. |
| Wire or repair | An existing component, state transition, or server operation can support it with a small connection or logic repair. |
| Build UI | The server capability exists, but the page, controls, or client workflow need implementation. |
| Build API + UI | The domain or CLI may exist, but the browser needs a server operation or management contract as well as a UI. |

These are scope estimates, not time estimates. A control can need little code and still need a careful regression test.

## Suggested order

1. Repair controls that already promise a working result: absolute ranges, cardinality, stored-run full results, chart result selection and timestamp conversion, and Runs pagination. These have direct browser reproductions.
2. Connect small existing pieces: the second Save, a consistent editor Save input, Stop live, error/count state, a useful Help link, the theme shortcut, and the duplicate Schema navigation if it should open the inspector.
3. Build browser workflows over existing services: Health, schedule window/lag editing, history export, catalog administration, and catalog autocomplete. Treat visualization support for non-time aggregations as a defined feature rather than assuming one chart can consume every result.
4. Design the larger management additions: Sources, Retention, Users/API tokens, editable Profile, and persistent Notifications. They need server contracts and ownership decisions as well as screens. Decide mobile support before extending the desktop layout further.

The implementation paths show that Trawl does not need a new query engine, scheduler, schema catalog, export engine, or key store to finish the web UI. Most gaps are in browser state, data conversion, and missing management workflows. Sources and retention management still need an explicit configuration API; an existing config file is not such an API.
